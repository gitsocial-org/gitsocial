# S3 Remote Backend

Any S3-compatible bucket (AWS S3, Cloudflare R2, Hetzner, etc.) is a git remote through the `s3://` remote helper ([GITMSG.md §1.3](../specs/GITMSG.md#13-reference-sections)) and can serve the repository's [static site](STATIC-SITE.md).

[Clone](#clone) · [Push](#push) · [Thin fork buckets](#thin-fork-buckets) · [Local development](#local-development) · [Testing](#testing-against-a-provider) · [Reference](#reference)

## Clone

```bash
git clone https://<bucket-domain>/                                  # stock git, public bucket
gitsocial clone s3://<endpoint>/<bucket>/<prefix>                   # through the helper; private buckets work
git config --global alias.remote-s3 '!gitsocial __git-remote-s3'   # once, for bare `git clone s3://...`
```

- Stock git works because the bucket is a dumb-HTTP git repository.
- `gitsocial clone` signs its reads with your credentials, so a private bucket works. With no credentials configured it reads unsigned instead, so a public bucket clones and fetches without any: see [anonymous reads](#anonymous-reads).
- Clones, and workspaces whose origin is a bucket, get the `remote-s3` alias in their local git config. The global alias is for `git clone s3://` anywhere else.

## Push

```bash
gitsocial config credentials set <endpoint-host>                        # paste the access key and the secret key
gitsocial remote add s3://<endpoint>/<bucket>/<prefix> --default --site  # default push target, site on
gitsocial push
```

- URLs are stored as `s3://<endpoint-host>/<bucket>/<prefix>`. `remote add` and `clone` also take a provider's `https://` endpoint or virtual-host URL and a pasted AWS console URL. A self-hosted endpoint needs the `s3://` form.
- `--default` appends the remote to `gitsocial.pushRemote`; `--site` sets `site.publish` (see [STATIC-SITE.md](STATIC-SITE.md#publish)).
- An `s3://` URL added with plain `git remote add` works too.
- Credentials are stored per endpoint host. `credentials list` shows them with masked keys; `credentials remove <host>` deletes one.

`gitsocial push [remote...]` publishes the `gitmsg/*` data branches, the `refs/gitmsg/*` state refs, all tags, the default branch when it is ahead, the heads of open pull requests, and on an s3 remote with `site.publish` the site.

- Remotes resolve in order: the arguments, then `gitsocial.pushRemote` (set with `gitsocial remote default <name...>`), then `origin` if it is an s3 remote, else the first s3 remote alphabetically, else `origin`.
- Several remotes push in turn. A failed remote is reported and skipped, and the command exits non-zero.
- Diverged `gitmsg/*` branches merge automatically. Diverged code branches fail with a hint.
- Output: `Pushed to <remote> (<url>)`, then `Site: published`, `Site: skipped (<reason>)` or `Site: failed: <err>`. A site failure after a successful data push is a warning.
- A plain `git push` to an s3 remote maintains the site too, since `site.publish` lives in the pushed config ref.

| Flag | Effect |
|---|---|
| `--no-code` | skip code branches |
| `--all-branches` | publish every local branch; a non-fast-forward branch is reported and not merged; reconcile with `git push --force-with-lease` |
| `--no-site` | skip the site for this push |
| `--site-only` | rebuild the site, push no data |
| `--full` | detach a [thin fork bucket](#thin-fork-buckets) |
| `--dry-run` | print the plan, touch nothing, stay offline |

`url`, `publish` and `pages` can differ per remote; see [per-remote overrides](STATIC-SITE.md#per-remote-overrides).

## Thin fork buckets

A fork pushed to its own bucket normally carries all of upstream's history. A thin bucket carries only the fork's own objects and records where the rest is. `gitsocial fork create` with a bucket destination sets one up; by hand, set two keys on the remote:

```bash
git config remote.<name>.gitsocial-thin true
git config remote.<name>.gitsocial-upstream https://github.com/org/repo
```

- A thin push fetches upstream first to learn what it can leave out. When upstream is unreachable it uses the tips recorded in the bucket, and failing that pushes everything, with a note.
- `gitmsg/*` and `refs/gitmsg/*` are pushed complete, so issues, comments and PR metadata do not need upstream.
- The upstream must be `https://`, `http://` or `s3://`. Anything else, or no upstream at all, means a full push with a note. The URL is bucket content, so its transport is checked before any fetch runs. `ssh://` is not accepted: the recorded URL is the one a reader fetches anonymously.
- A reader that hits a missing object fetches it from the upstream recorded in `.gitsocial/upstream`. The fetch runs once per session into `refs/remotes/upstream/*`, with `upstream` registered as a real remote, so the borrowed objects stay reachable and a later `git gc` cannot corrupt the clone. There is no per-object resolver; the fetch is the overlay.
- `--full` uploads the missing objects loose rather than packed. It is a one-time repair, the dumb walker prefers loose keys, and the next sealing round packs them.
- `gitsocial status` shows `Thin fork of <url>, pinned at <n> tips`.
- `gitsocial push --full` detaches the bucket: it uploads every object, restores `info/refs`, deletes `.gitsocial/upstream` and clears the flag.

| Surface | Full bucket | Thin bucket |
|---|---|---|
| `gitsocial clone s3://`, `git clone s3://` via the alias | works | works: fetches upstream, then overlays |
| `git clone https://<bucket-domain>/` | works | fails at ref discovery; `info/refs` is not written |
| Static site | on `site.publish` | refused; an existing site stays, unmaintained |
| `gitsocial fetch` of fork metadata | works | works without upstream |

## Local development

```bash
go build -o bin/locals3 ./library/core/objstore/locals3
bin/locals3 -root <dir>          # 127.0.0.1:9000; each subdirectory of -root is a bucket
```

A loopback host (`s3://127.0.0.1:9000/<bucket>/<prefix>`) needs only dummy keys and defaults to http and path-style; any IP-literal host defaults to path-style. Another dev server takes `GITSOCIAL_S3_ENDPOINT=http://...` and `GITSOCIAL_S3_PATH_STYLE=1`. The same port serves a pushed site at `http://127.0.0.1:9000/<bucket>/<prefix>/`.

## Testing against a provider

Verified on AWS S3, Cloudflare R2 and DigitalOcean Spaces. Export credentials in the environment only, one provider at a time.

```bash
GITSOCIAL_TEST_FULL=1 GITSOCIAL_S3_TEST_HOST=<host> GITSOCIAL_S3_TEST_BUCKET=<bucket> \
  go test ./cli/gitsocial -run TestS3Helper_realBucket -v
```

Hosts: `s3.<region>.amazonaws.com`, `<account-id>.r2.cloudflarestorage.com`, `<region>.digitaloceanspaces.com`. Pass is `provider round trip OK`; the test cleans up after itself.

The manual flow from a fresh shell, credentials exported and nothing else configured:

```bash
git init uxdemo && cd uxdemo && git commit --allow-empty -m init
gitsocial remote add "$REMOTE" && gitsocial config site set publish true
gitsocial social post "hello from a bucket" && gitsocial push       # Pushed, Commits 1, Site: published
git push origin main                                                 # plain git through the recorded alias
cd .. && gitsocial clone "$REMOTE" uxclone && cd uxclone
git fsck --strict && gitsocial fetch && gitsocial social timeline    # the post is there
```

`GITSOCIAL_S3_DEBUG=1` dumps every request and response to stderr. Manual prefixes need manual deletion.

## Reference

### Bucket layout

| Keys | Contents |
|---|---|
| `objects/<xx>/<38-hex>` | loose git objects |
| `objects/pack/pack-<hash>.{pack,idx}` | [packfiles](#packfiles) and their indexes |
| `refs/...`, `HEAD` | one key per ref, or a `.gen/<counter>` chain in generation mode, plus the `HEAD` symref |
| `info/refs`, `objects/info/packs` | the dumb-HTTP ref listing and pack list, rewritten on every ref-moving push |
| `objects/info/http-alternates`, `objects/info/alternates` | present and empty; git's dumb walker probes them from a completion callback, where a 404 can livelock it |
| `.gitsocial/refs.json` | refname to sha for every ref in the bucket, rewritten after every ref-moving push, created or reconciled before one, and rebuilt by `gitsocial push --site-only`; the ref source for readers that cannot list, [anonymous](#anonymous-reads) or not, and for the [static site](STATIC-SITE.md) |
| `.gitsocial/ref-mode`, `.gitsocial/pack-state.json`, `.gitsocial/packmap/<xx>.json`, `.gitsocial/upstream` | the ref mode, the sealing state, the pack map, the thin-fork marker |
| the shell files at the root, the page directories, `.gitsocial/site/` | the static site; every key is listed in [STATIC-SITE.md](STATIC-SITE.md#reference) |
| `artifacts/<version>/...`, `artifacts/latest.txt` | release artifacts and the newest version marker, written by [`gitsocial release artifacts push`](RELEASE.md#artifacts) |

These names are reserved. Repo content does not claim them. Site maintenance deletes only keys it generated, so artifacts and other root objects survive every push.

### Ref update modes

The first writer pins the mode in `.gitsocial/ref-mode` from the endpoint host's provider; an unknown host is probed. A bucket without conditional writes is rejected before any ref is written.

| Mode | Mechanism | Providers |
|---|---|---|
| `etag` | one key per ref, updated with `If-Match` | AWS, R2 |
| `generation` | create-only chain `<ref>/.gen/<counter>`; the highest generation wins; the newest two are kept | Spaces |

Fast-forward is enforced by the helper. `git push --force-with-lease` works in both modes.

### Packfiles

| Objects in a push | Upload |
|---|---|
| under `GITSOCIAL_S3_PACK_THRESHOLD` (default 1,000) | one loose key per object |
| at or above it | two packfiles: commits and tags at `--depth=0`, trees and blobs at git's default depth |

Post-push maintenance seals loose objects into packs every 25 ref-moving pushes, or once about 64 objects are loose, and deletes the loose copies after 3 further pushes and 1 hour. A shallow or partial clone does not seal. A pack over 4 GiB falls back to loose objects; there is no multipart upload. The delta falls back as one unit, so no push leaves half of itself packed.

The commits and tags pack is written at `--depth=0`, so one ranged read of a commit returns a self-contained stream. A delta of 2,000 objects or more first lists `objects/` and drops what the bucket already holds, so an interrupted first push resumes; below that the listing costs more than the repeated PUTs. `pack.indexVersion=2` and `pack.packSizeLimit=0` are pinned on the `pack-objects` command line, so a pusher's own git config cannot change the shape of an artifact every reader depends on.

A pack's per-object byte ranges are published into the pack map; a shard that will not write is logged and nothing more, since a reader with no map entry range-reads the `.idx` instead.

### Sealing

Sealing is the one place the backend deletes an immutable key. Every step is idempotent, and a failure leaves the bucket as it was and is retried by the next push.

- What is packable is derived from the bucket ref tips this clone can resolve. A refname the clone does not carry contributes nothing rather than failing the pass, since a bucket has several pushers.
- `.gitsocial/pack-state.json` is rewritten under compare-and-swap, so two pushers finishing at once merge their rounds instead of dropping each other's. A document at another schema version is an error rather than an overwrite, since overwriting it would strand a pending round's loose copies beside their packs.
- A sealed round's loose copies go only after a fresh read of `objects/info/packs` proves its packs are listed there. That listing is how both readers discover a pack, and concurrent pushers rewrite it from whole snapshots.
- The grace is a push count and a wall-clock hour, and both must clear. The count is the half no clock skew can move; the window is advisory, since a bucket has no shared clock.
- A round is deleted as one unit. A pack of the round missing from the bucket fails the round rather than collecting the rest, which would leave loose copies with nothing tracking them.
- Each round writes new packs and leaves what an earlier round packed alone, so repeated seals accumulate packfiles. Consolidating them is out of scope.
- A seal attempt records its failure on the bucket, and every later push repeats it until a seal succeeds. A helper's stderr scrolls past unread.

### Push maintenance

Every ref-moving push runs a best-effort upkeep pass. It runs after the push report, so its outcome cannot fail or delay the git push.

- The per-ref report and its terminating blank line are flushed to git before the pass starts. Git blocks on that report, so maintenance ahead of the flush reads as a hang and can make updated refs look failed.
- One `gitsocial push` is several git pushes in a row. All but the last set `GITSOCIAL_S3_DEFER_MAINTENANCE`, so the pass runs once against the final ref state. A plain `git push` sets nothing and runs it every time.
- The pass advertises the repo's own HEAD symref as the bucket HEAD, not an assumed `main`, and keeps an existing HEAD unless it points at a `gitmsg/*` branch. A HEAD naming a ref the bucket does not carry is repointed to a branch it does carry.
- `info/refs` and `objects/info/packs` refresh on every ref-moving push, whether or not the site is on, so stock git keeps cloning.
- The site's own share of the pass, and the marker that lets it skip, are in [STATIC-SITE.md](STATIC-SITE.md#push-time-maintenance).
- Every mutable JSON document two pushers can touch is rewritten under compare-and-swap: read with the key's ETag, merge, write only if nothing moved, and replay the merge on contention. A provider that cannot update conditionally takes an unconditional write instead, which is the last-writer-wins behavior this replaces. A document that is present but does not parse fails the read rather than reading as absent, so nothing writes a zeroed one over it.

### Fetch

`gitsocial clone` and `gitsocial fetch` walk the object graph from the wanted tips and write objects straight into `GIT_DIR/objects`. Loose objects are stored in the bucket in git's own format, so a download is a verbatim copy and no sha is rewritten.

- A bucket whose bulk history is packed has its packfiles pulled and indexed with `git index-pack` once per session, so the walk resolves those objects from the local odb rather than 404ing on each. A pack lands under a temporary name and is renamed into place only once indexed, so an interrupted download leaves git no pack it cannot read.
- An object the local odb already holds counts as present and its graph is assumed complete, which is the assumption git's own haves negotiation makes. An object that came in through a pulled packfile does not: a pack need not close over its own references, so the walk descends through it.
- The empty tree is the exception to the presence probe: `cat-file` answers for it whether or not the odb holds a copy, so reading it as present would stop the walk from downloading the bucket's own. Every `gitmsg/*` commit has that tree.
- On a bucket that can list, a ref's value is proved without a GET when the manifest claims it and the listing's ETag is the MD5 of the `<sha>\n` body that claim implies. Only a true match is trusted, so a wrong manifest cannot poison a ref value; a multipart-shaped ETag, a mismatch, or a generation chain falls back to the read.

### Cache policy

Every upload carries `Cache-Control`. The local servers derive the same headers from the key pattern.

| Keys | `Cache-Control` |
|---|---|
| loose objects, packfiles and indexes, release artifacts, and the site's sealed shards, sealed pages and sitemap parts | `public, max-age=31536000, immutable` |
| every mutable key: refs, `HEAD`, the `.gitsocial/` state, `info/refs`, `objects/info/packs`, `artifacts/latest.txt`, and every other site key | `no-cache` |

Immutable keys are not rewritten. The one deletion is a loose object whose pack has been sealed and whose grace has passed.

`Cache-Control` is stamped on every PUT at one chokepoint, derived from the key, so the git-push and site-push paths cannot disagree. It is not a signed header, so it does not affect SigV4.

### Request behavior

- Every request retries a transient fault with bounded backoff: a 429, any 5xx, the 400 AWS documents as a retryable stalled upload, and a transport-level failure that carried no status. A 404, a 403, a precondition failure and every other 4xx are definite answers and return at once.
- Writes retry as well as reads: a PUT of the same key and the same bytes is idempotent, so a retry either lands or fails for good. One throttled PUT would otherwise fail a whole publish.
- A CDN that compresses a response on the fly marks its ETag weak. The `W/` prefix is stripped before the value is used, since `If-Match` matches no weak ETag, and the value inside is still the object's own.
- The HTTP transport keeps 64 idle connections per host, so the concurrent upload pool does not open a fresh TLS handshake each round.

### Thin bucket marker

`.gitsocial/upstream`, rewritten after every successful thin push:

```json
{"version": 1, "url": "https://github.com/alice/repo", "pins": [{"ref": "refs/heads/main", "sha": "..."}]}
```

### Credentials

Resolved per endpoint host, in this order: `GITSOCIAL_S3_ACCESS_KEY` with `GITSOCIAL_S3_SECRET_KEY`, then `~/.config/gitsocial/credentials.json`, then `AWS_ACCESS_KEY_ID` with `AWS_SECRET_ACCESS_KEY`. A tier counts only when both halves are set, so a lone variable is skipped rather than mixed with another tier; when no tier is complete the client is [anonymous](#anonymous-reads).

The file honors `XDG_CONFIG_HOME` and is an object keyed by endpoint host (`<account>.r2.cloudflarestorage.com`, `s3.<region>.amazonaws.com`, `127.0.0.1:9000`) with `{"accessKey": "...", "secretKey": "..."}` values. It is written `0600`; a looser mode gets a warning. A missing file is fine; a malformed one warns once and falls through to the environment.

### Anonymous reads

With no credentials for the endpoint host, the client is anonymous: it signs nothing and reads only. A push refuses with the credentials message before it uploads anything.

A public bucket normally grants `s3:GetObject` but not `s3:ListBucket`, which breaks two assumptions. Ref discovery cannot list `refs/`, so it takes the ref names from the first document the bucket publishes: `.gitsocial/refs.json`, then `info/refs`, then the copy older pushes wrote under `.gitsocial/site/`. And an absent key answers 403 rather than 404, so a 403 on a read folds into "not found" (`ErrAccessDenied` wraps `ErrNotFound`), keeping the thin-fork overlay and the pack probes working. A signed key without `s3:ListBucket` takes the same path; a signed 403 folds only when the provider reports `AccessDenied`, so a rejected credential keeps its own error.

- In [etag mode](#ref-update-modes) each name's own key is read for its value, so a stale document can omit a ref, or name one deleted since, but cannot yield a wrong sha. In generation mode a chain's tip is only found by listing, so the document's claim is the value, and a ref deleted since the last push stays visible until the next one.
- The manifest is rewritten from the push's own ref view after every ref-moving transfer. Before a push, the helper's listing also creates or reconciles it, so a push that moves nothing still leaves a current one. That write happens before git decides whether anything is pushed.
- In etag mode the manifest write is conditional on the document as it stood before the push, so a concurrent pusher's manifest forces a fresh listing rather than being overwritten. A generation-mode bucket cannot write conditionally: two pushes landing in the same instant can leave it one push behind until the next push, as can a write that fails on a transfer after which nothing moves.
- A document that is present and empty means zero refs. Discovery stops there instead of falling through to an older source.
- A bucket last pushed before `.gitsocial/refs.json` existed still reads through its site copy or `info/refs`. A [thin fork bucket](#thin-fork-buckets) has neither, so it needs one push from a current gitsocial first.
- When no document is readable, the ref-mode marker and `HEAD` decide the diagnosis: readable means a bucket that needs one push from a current gitsocial, unreadable means a private bucket or one nothing was pushed to, and the error names the credentials to set.
- Anonymous reads need no `s3:ListBucket`; adding it also works.
