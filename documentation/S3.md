# S3 Remote Backend

Any S3-compatible bucket (AWS S3, Cloudflare R2, Hetzner, etc.) is a git remote through the `s3://` remote helper ([GITMSG.md §1.3](../specs/GITMSG.md#13-reference-sections)) and can serve the repository's [static site](STATIC-SITE.md).

[Clone](#clone) · [Push](#push) · [Thin fork buckets](#thin-fork-buckets) · [Local development](#local-development) · [Testing](#testing-against-a-provider) · [Reference](#reference)

## Clone

```bash
git clone https://<bucket-domain>/                                  # stock git, public bucket
gitsocial clone s3://<endpoint>/<bucket>/<prefix>                   # through the helper; private buckets work
git config --global alias.remote-s3 '!gitsocial __git-remote-s3'   # once, for bare `git clone s3://...`
```

- Stock git works because the bucket is a dumb-HTTP git repository.
- `gitsocial clone` signs its reads with your credentials, so a private bucket works.
- Clones, and workspaces whose origin is a bucket, get the `remote-s3` alias in their local git config. The global alias is for `git clone s3://` anywhere else.

## Push

```bash
gitsocial config credentials set <endpoint-host>                        # paste the access key and the secret key
gitsocial remote add s3://<endpoint>/<bucket>/<prefix> --default --site  # default push target, site on
gitsocial push
```

- URLs are stored as `s3://<endpoint-host>/<bucket>/<prefix>`. `remote add` and `clone` also take a provider's `https://` endpoint or virtual-host URL and a pasted AWS console URL. A self-hosted endpoint needs the `s3://` form.
- `--default` appends the remote to `gitsocial.pushRemote`; `--site` sets `site.publish` (see [STATIC-SITE.md](STATIC-SITE.md#publish)).
- An `s3://` URL added with plain `git remote add` works too.
- Credentials are stored per endpoint host. `credentials list` shows them with masked keys; `credentials remove <host>` deletes one.

`gitsocial push [remote...]` publishes the `gitmsg/*` data branches, the `refs/gitmsg/*` state refs, all tags, the default branch when it is ahead, the heads of open pull requests, and on an s3 remote with `site.publish` the site.

- Remotes resolve in order: the arguments, then `gitsocial.pushRemote` (set with `gitsocial remote default <name...>`), then `origin` if it is an s3 remote, else the first s3 remote alphabetically, else `origin`.
- Several remotes push in turn. A failed remote is reported and skipped, and the command exits non-zero.
- Diverged `gitmsg/*` branches merge automatically. Diverged code branches fail with a hint.
- Output: `Pushed to <remote> (<url>)`, then `Site: published`, `Site: skipped (<reason>)` or `Site: failed: <err>`. A site failure after a successful data push is a warning.
- A plain `git push` to an s3 remote maintains the site too, since `site.publish` lives in the pushed config ref.

| Flag | Effect |
|---|---|
| `--no-code` | skip code branches |
| `--all-branches` | publish every local branch; a non-fast-forward branch is reported, never merged; reconcile with `git push --force-with-lease` |
| `--no-site` | skip the site for this push |
| `--site-only` | rebuild the site, push no data |
| `--full` | detach a [thin fork bucket](#thin-fork-buckets) |
| `--dry-run` | print the plan, touch nothing, stay offline |

`url`, `publish` and `pages` can differ per remote; see [per-remote overrides](STATIC-SITE.md#per-remote-overrides).

## Thin fork buckets

A fork pushed to its own bucket normally carries all of upstream's history. A thin bucket carries only the fork's own objects and records where the rest is. `gitsocial fork create` with a bucket destination sets one up; by hand, set two keys on the remote:

```bash
git config remote.<name>.gitsocial-thin true
git config remote.<name>.gitsocial-upstream https://github.com/org/repo
```

- A thin push fetches upstream first to learn what it can leave out. When upstream is unreachable it uses the tips recorded in the bucket, and failing that pushes everything, with a note.
- `gitmsg/*` and `refs/gitmsg/*` are always pushed complete, so issues, comments and PR metadata never need upstream.
- The upstream must be `https://`, `http://` or `s3://`; anything else, or no upstream at all, means a full push with a note.
- A reader that hits a missing object fetches it from the upstream recorded in `.gitsocial/upstream`.
- `gitsocial status` shows `Thin fork of <url>, pinned at <n> tips`.
- `gitsocial push --full` detaches the bucket: it uploads every object, restores `info/refs`, deletes `.gitsocial/upstream` and clears the flag.

| Surface | Full bucket | Thin bucket |
|---|---|---|
| `gitsocial clone s3://`, `git clone s3://` via the alias | works | works: fetches upstream, then overlays |
| `git clone https://<bucket-domain>/` | works | fails at ref discovery; `info/refs` is not written |
| Static site | on `site.publish` | refused; an existing site stays, unmaintained |
| `gitsocial fetch` of fork metadata | works | works without upstream |

## Local development

```bash
go build -o bin/locals3 ./library/core/objstore/locals3
bin/locals3 -root <dir>          # 127.0.0.1:9000; each subdirectory of -root is a bucket
```

A loopback host (`s3://127.0.0.1:9000/<bucket>/<prefix>`) needs only dummy keys and defaults to http and path-style; any IP-literal host defaults to path-style. Another dev server takes `GITSOCIAL_S3_ENDPOINT=http://...` and `GITSOCIAL_S3_PATH_STYLE=1`. The same port serves a pushed site at `http://127.0.0.1:9000/<bucket>/<prefix>/`.

## Testing against a provider

Verified on AWS S3, Cloudflare R2 and DigitalOcean Spaces. Export credentials in the environment only, one provider at a time.

```bash
GITSOCIAL_TEST_FULL=1 GITSOCIAL_S3_TEST_HOST=<host> GITSOCIAL_S3_TEST_BUCKET=<bucket> \
  go test ./cli/gitsocial -run TestS3Helper_realBucket -v
```

Hosts: `s3.<region>.amazonaws.com`, `<account-id>.r2.cloudflarestorage.com`, `<region>.digitaloceanspaces.com`. Pass is `provider round trip OK`; the test cleans up after itself.

The manual flow from a fresh shell, credentials exported and nothing else configured:

```bash
git init uxdemo && cd uxdemo && git commit --allow-empty -m init
gitsocial remote add "$REMOTE" && gitsocial config site set publish true
gitsocial social post "hello from a bucket" && gitsocial push       # Pushed, Commits 1, Site: published
git push origin main                                                 # plain git through the recorded alias
cd .. && gitsocial clone "$REMOTE" uxclone && cd uxclone
git fsck --strict && gitsocial fetch && gitsocial social timeline    # the post is there
```

`GITSOCIAL_S3_DEBUG=1` dumps every request and response to stderr. Manual prefixes need manual deletion.

## Reference

### Bucket layout

| Keys | Contents |
|---|---|
| `objects/<xx>/<38-hex>` | loose git objects |
| `objects/pack/pack-<hash>.{pack,idx}` | [packfiles](#packfiles) and their indexes |
| `refs/...`, `HEAD` | one key per ref, or a `.gen/<counter>` chain in generation mode, plus the `HEAD` symref |
| `info/refs`, `objects/info/packs` | the dumb-HTTP ref listing and pack list, rewritten on every ref-moving push |
| `objects/info/http-alternates`, `objects/info/alternates` | empty on purpose; git's dumb walker probes them |
| `.gitsocial/ref-mode`, `.gitsocial/pack-state.json`, `.gitsocial/packmap/<xx>.json`, `.gitsocial/upstream` | the ref mode, the sealing state, the pack map, the thin-fork marker |
| the shell files at the root, the page directories, `.gitsocial/site/` | the static site; every key is listed in [STATIC-SITE.md](STATIC-SITE.md#reference) |
| `artifacts/<version>/...`, `artifacts/latest.txt` | release artifacts and the newest version marker, written by [`gitsocial release artifacts push`](RELEASE.md#artifacts) |

These names are reserved; repo content never claims them. Site maintenance deletes only keys it generated, so artifacts and other root objects survive every push.

### Ref update modes

The first writer pins the mode in `.gitsocial/ref-mode` from the endpoint host's provider; an unknown host is probed. A bucket without conditional writes is rejected before any ref is written.

| Mode | Mechanism | Providers |
|---|---|---|
| `etag` | one key per ref, updated with `If-Match` | AWS, R2 |
| `generation` | create-only chain `<ref>/.gen/<counter>`; the highest generation wins; the newest two are kept | Spaces |

Fast-forward is enforced by the helper. `git push --force-with-lease` works in both modes.

### Packfiles

| Objects in a push | Upload |
|---|---|
| under `GITSOCIAL_S3_PACK_THRESHOLD` (default 1,000) | one loose key per object |
| at or above it | two packfiles: commits and tags at `--depth=0`, trees and blobs at git's default depth |

Post-push maintenance seals loose objects into packs every 25 ref-moving pushes, or once about 64 objects are loose, and deletes the loose copies after 3 further pushes and 1 hour. A shallow or partial clone never seals. A pack over 4 GiB falls back to loose objects; there is no multipart upload.

### Cache policy

Every upload carries `Cache-Control`. The local servers derive the same headers from the key pattern.

| Keys | `Cache-Control` |
|---|---|
| loose objects, packfiles and indexes, release artifacts, and the site's sealed shards, sealed pages and sitemap parts | `public, max-age=31536000, immutable` |
| every mutable key: refs, `HEAD`, the `.gitsocial/` state, `info/refs`, `objects/info/packs`, `artifacts/latest.txt`, and every other site key | `no-cache` |

Immutable keys are never rewritten. The one deletion is a loose object whose pack has been sealed and whose grace has passed.

### Thin bucket marker

`.gitsocial/upstream`, rewritten after every successful thin push:

```json
{"version": 1, "url": "https://github.com/alice/repo", "pins": [{"ref": "refs/heads/main", "sha": "..."}]}
```

### Credentials

Resolved per endpoint host, in this order: `GITSOCIAL_S3_ACCESS_KEY` with `GITSOCIAL_S3_SECRET_KEY`, then `~/.config/gitsocial/credentials.json`, then `AWS_ACCESS_KEY_ID` with `AWS_SECRET_ACCESS_KEY`.

The file honors `XDG_CONFIG_HOME` and is an object keyed by endpoint host (`<account>.r2.cloudflarestorage.com`, `s3.<region>.amazonaws.com`, `127.0.0.1:9000`) with `{"accessKey": "...", "secretKey": "..."}` values. It is written `0600`; a looser mode gets a warning. A missing file is fine; a malformed one warns once and falls through to the environment.

### Environment variables

| Variable | Meaning |
|---|---|
| `GITSOCIAL_S3_ACCESS_KEY`, `GITSOCIAL_S3_SECRET_KEY` | credentials; both required; beat the file |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | credential fallback after the file |
| `GITSOCIAL_S3_ENDPOINT`, `GITSOCIAL_S3_PATH_STYLE` | endpoint scheme and path-style addressing for self-hosted servers |
| `GITSOCIAL_S3_REGION` | SigV4 region for a host no preset recognizes |
| `GITSOCIAL_S3_CONCURRENCY` | concurrent uploads per push; default 16; overrides the `s3.concurrency` setting |
| `GITSOCIAL_S3_DEBUG=1` | dump every request and response to stderr |
| `GITSOCIAL_S3_PACK_THRESHOLD` | objects per push at which a push uploads packfiles; default 1,000; also the sealing minimum, default 64 |
| `GITSOCIAL_SITE_SHARD_COUNT`, `GITSOCIAL_SITE_WALK_BUDGET` | test-fixture overrides: sealed shard size (default 4,000) and per-push walk budget (default 50,000) |
| `GITSOCIAL_SITE_PAGES_BUDGET`, `GITSOCIAL_SITE_SITEMAP_PART` | test-fixture overrides: pages per push (default 5,000) and sitemap part size (default 40,000) |
